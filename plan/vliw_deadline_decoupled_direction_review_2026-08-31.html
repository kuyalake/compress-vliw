2. 第三篇指令流及 trace 的核心事实

第三篇架构每周期发射一条固定 184-bit VLIW：

槽位位宽主要功能
LOAD42 bit存储器到寄存器的数据搬运及格式控制
STORE42 bit寄存器到存储器的数据搬运及格式控制
VECTOR34 bitRFU、向量算术和归约控制
SCALAR31 bitBFU/标量路径控制
SFU31 bit特殊函数单元控制
CONTROL4 bit保留位及 EOP

稳定的稀疏性

  • 位宽加权有效槽利用率：9.3%–30.7%。
  • 平均每周期约 0.5–1.6 个有效执行槽。
  • 局部单周期峰值仍可能达到 5 个有效槽。
  • 旧的 6-bit ifnull + 原样有效槽口径为 22.28%；改用 5-bit 功能 mask 并由周期计数隐式产生 EOP 后约为 21.74%。

明显的异构性

  • 每条 trace 实际出现 7–27 种 mask，熵为 2.0–3.4 bit/cycle；合法编码空间不是 64 种，而是 32 种五功能槽组合加 1 种独立 EOP，共 33 种。
  • LOAD/STORE 控制组合各 1 种。
  • VECTOR 最多 7 种，SCALAR 最多 6 种，SFU 最多 2 种。
  • 完整寄存器/地址组合变化较大，但少量相邻差值模式高频出现。

不能据此成立的假设

  • Softmax 的严格周期核覆盖只有约 2.0%–3.7%，LayerNorm 只有约 0.9%–1.7%，不存在覆盖全部 workload 的通用周期生成器。
  • 完整槽位字典会受到 256 深度寄存器地址变化影响，不能假设完整指令经常重复。
  • 现有 10.02% 的字段混合编码结果是软件自由选择 RAW/DICT/DELTA 的上界，不是已经可实现的硬件格式。
  • Li padded external storage 的 47.02% 不能与片上逻辑位数直接比较。保留 Li 类 6-bit ifnull + 有效原始 payload 的 22.28% 作为文献口径；针对本平台利用 CONTROL 只在末尾 EOP 出现的事实，工程基线应改为 5-bit 功能 mask + 隐式 EOP，约 21.74%。

3. 建议定义的一般性研究问题

对于每周期必须发射一条超宽指令、但每周期只有少量异构槽位有效的静态调度处理器，如何在给定存储读取带宽和有限恢复硬件的条件下压缩存储指令流，并保证每个有效槽都在原定周期之前恢复完成，从而保持逐周期行为完全不变？

相关术语解释：

  • 槽事件：某个周期中某个非空槽位。例如周期 10 的 VECTOR 操作就是一个槽事件。
  • 恢复期限：这个事件必须在哪个原始执行周期前恢复完成。
  • 前瞻恢复：不等到执行周期才解压，而是提前恢复并放入 FIFO。
  • 压缩驻留：片上指令存储器保存压缩格式，而不是装载后重新展开成 184-bit。
  • 周期精确：第 t 周期的有效操作与原 trace 第 t 周期一致，不插入气泡，也不重新调度。

4. 推荐压缩格式

4.1 周期日历

每个原始周期保留一条有效槽 mask。日历只描述时间关系，不负责保存具体操作，因此压缩不会删除或移动原始执行周期。

第一版使用紧凑打包的 5-bit 功能 mask，依次表示 LOAD/STORE/VECTOR/SCALAR/SFU。CONTROL 只在最后一条 EOP 指令为 1，因此由函数描述符中的总周期数在末周期隐式产生 EOP，不再逐周期保存第六位。

mask 模板只保留为消融实验：

  • 每个函数选择最多 15 种高频 mask；
  • 每周期使用固定 4-bit 索引；
  • 第 16 个编码表示 escape，随后保存原始 5-bit 功能 mask。

当前 12 条 trace 上，不计模板表本身时，4-bit 模板 + escape 平均需要约 4.09 bit/cycle，相对固定 5-bit mask 仅节省约 0.91 bit/cycle。它只使原始 184-bit 指令容量再下降约 0.50 个百分点、使 21.74% 的 mask+raw 基线相对改善约 2.3%；考虑模板表和 decode MUX 后净收益更小，因此不建议进入主格式。

4.2 主格式使用 RAW payload，delta 仅作后期小优化

现有 10.02% 字段混合结果允许每条 trace、每个字段分别选择 RAW/DICT/DELTA 及字典内容，属于 per-trace oracle，不能作为跨 workload 通用格式。第一版对有效槽保存 RAW payload，不使用普通值字典，也不对 VECTOR/SCALAR 寄存器建立逐 workload delta 表。

后期只考虑一个固定、小规模且带 RAW escape 的 delta fast path：

  • LOAD/STORE：28-bit mem_addr 与 8-bit gpr_addr；
  • SFU：8-bit dst/src gpr 地址；
  • 所有 workload 使用相同的 1–2 bit 固定 delta 码，不允许逐 workload 建表；
  • 未命中时通过 escape 在 RAW 流中补充完整地址。
Address_i = (Address_(i-1) + DeltaCode) mod 2^W

编码约束：若 escape 占用同一个 b-bit 码字，只能容纳 2^b−1 种常用 delta。因此 2-bit 只能直接表示 3 种 delta + 1 个 escape；若要保留 4 种 delta，必须另加 escape 标志/位图。1-bit 同理只能表示 1 种 delta + 1 个 escape。

硬件代价：需要 LOAD/STORE 的 28-bit 地址模加法器、相应 8-bit gpr 地址加法器，以及 SFU dst/src 的 8-bit 加法器、历史状态寄存器和 escape MUX。这里是定宽整数/地址模加法，而不是数值数据通路中的定点乘加；仍必须综合其面积、功耗和时序，确认不会抵消存储收益。

4.3 保底模式

mask + 原始有效槽现在是主格式而非少见保底。后期 delta fast path 若未命中或压缩结果变差，就通过 escape 返回完整地址。这样正确性不依赖统计规律，最坏情况只损失少量标签位。

4.4 入口状态

只在真实的函数、tile 或循环入口保存初始操作数、压缩流指针和小表内容。第一版不建议每 64 周期设置完整随机访问检查点，因为完整检查点还需要五个槽状态和多个流指针，此前约 0.1 个百分点的数字没有包含这些元数据。

Reservoir 是接收 64-bit 存储行的小缓冲，用于处理记录跨存储行和短时突发。主格式直接前瞻读取 RAW 有效槽并放入相应 FIFO；后期可选 delta 单元只处理 LOAD/STORE mem/gpr 地址和 SFU gpr 地址，并从独立 escape 流取得未命中的完整值。

执行侧不访问字典，也不做地址加法；它只读取当前 mask、从有效槽 FIFO 中 pop、对无效槽填 0。若实现可选 delta，定宽模加法器放在前瞻恢复级并与执行发射关键路径隔离。

6. 周期精确恢复原理

对任意槽位 s，压缩器按照原 trace 顺序保存该槽位的所有有效事件。到周期 t 之前，日历中槽位 s 的有效次数，恰好等于原 trace 中周期 0 到 t-1 的有效事件数。

  • 若周期 t 的 mask[s] 为 0，则输出空槽。
  • 若 mask[s] 为 1，则该槽 FIFO 的下一项必然对应原 trace 周期 t 的事件。
  • 控制字段由控制配置表精确恢复。
  • 操作数由原始值或模差精确恢复。

所以拼接后的整条 VLIW 与原 trace 同周期对应。该方案没有移动有效操作，也没有改变静态调度结果。

7.1 压缩读取需求

  • 不同 workload 的平均读取需求约为 12–43 bit/cycle。
  • 单周期峰值约为 60–124 bit。
  • 在忽略 SRAM 行对齐和读延迟的聚合模型中，64 bit/cycle 在 12 条 trace 上没有累计带宽欠账。
  • 峰值超过 64 bit 不代表一定停顿，因为较空闲周期可提前读取并积累在 Reservoir/FIFO 中。

7.3 尚未计入的现实因素

  • 64-bit 存储行对齐、跨行填充和物理浪费；
  • SRAM 读延迟和端口限制；
  • 日历、令牌、原始值三个逻辑流共享物理存储的仲裁；
  • 完整入口快照和跳转元数据；
  • 恢复器、FIFO、表寄存器的综合面积及功耗；
  • 存储宏最小宽度、最小深度导致的容量碎片。

因此建议的论文创新点是：

  1. 将压缩读取节奏与固定周期发射节奏解耦；
  2. 把槽事件建模为有执行期限的恢复任务；
  3. 用离线期限分析联合决定存储带宽、恢复路数和 FIFO 深度；
  4. 使用跨 workload 固定的 5-bit mask + RAW 格式；1–2 bit 地址 delta + RAW escape 只作为后期可选小优化，不以字段 oracle 为目标；
  5. 用少量普通宽度存储和前瞻恢复替代多个并行窄 bank，并用真实存储宏验证物理收益。

11. 四周 Go/No-Go 条件

建议只有同时满足以下条件才进入完整 RTL：

  1. 最终物理格式在全部 trace 上逐周期、逐位恢复通过；
  2. 包含 header、表、escape、填充以后，容量仍低于原始的约 25%；
  3. 加入真实 64-bit 行、1–2 拍 SRAM 延迟后仍能证明全程不下溢；
  4. 前端状态和 FIFO 保持在小规模，例如总体不超过约 1 KB；
  5. 恢复逻辑能够在流水化后达到 1 GHz，且不进入执行发射关键路径；
  6. 真实 IMEM + 恢复器的面积/能耗优于原始全宽 IMEM，也优于 Li 类多 bank 方案。

13. 最终判断与最大风险

三到四个月完成一个完整小论文具有可行性。 当前 trace 已确认稀疏需求，但旧受限令牌和 10%–13% 字段结果属于逐 trace oracle，不能再作为通用方案成立的证据。论文能否成立取决于统一格式下的物理存储、无停顿供给以及相对既有纵向压缩的可区分贡献；固定小 delta 只能作为后期优化和消融。

真正需要尽快回答的三个问题是：

  1. 最终序列化格式是否能够逐周期精确恢复？
  2. 真实 64-bit SRAM、读延迟和小缓冲是否能够全程无停顿？
  3. 压缩存储的节省是否能够覆盖恢复器、表和 FIFO 的面积与功耗？

如果三项均通过，建议继续；若真实 SRAM 宏填充后没有明显物理收益，则应及时停止，而不是继续在软件压缩率上堆复杂模式。
