1. 小白先读：这篇论文中的几个词是什么意思

词用最直白的话解释容易误解的地方
字典一张小表。表里保存若干个完整字段值；大程序中不再反复写这个字段，而只写它在表里的编号。字典不是软件里的字符串字典，而是处理器取指前面的小硬件存储。
并行字典宽指令被切成几块，每块各有一张字典；同一周期同时查多张表，再把结果拼回完整指令。“并行”指多张表同拍查，不是一次解压多条真正执行的 VLIW。
选择性压缩只有能省取指能耗的指令才压缩；很少重复或需要太多新字典项的指令保持原宽。因此同一个程序里会同时存在压缩指令和未压缩指令。
Bundle把连续的若干条“压缩后小指令”塞进一个原宽取指字。例如一次读出一个 64-bit 字，里面装三条压缩指令。这里的 bundle 是多个时间周期的压缩指令集合，不是“一条 VLIW 内的多个 slot”。
字典 Frame某一个循环区域要用的一套字典内容。程序进入这个区域前，先用特殊指令把这套内容写入硬件字典。换 frame 要花装载周期；字典并不是神奇地自动知道下一段程序需要什么。
静态压缩率磁盘/程序 SRAM 中总共存了多少 bit，除以未压缩程序的 bit。它决定容量，但不一定决定运行能耗。
动态压缩率程序真正运行时，从上一级指令存储取出的 bit 数，除以未压缩时的取指 bit 数。一个小循环会执行很多次，所以即使静态代码没变小，动态取指量仍可能明显下降。

表头说明：第一列是论文术语；第二列说明硬件实际做什么；第三列指出它与本课题“槽”和“Lane”的常见混淆。

2. Multanen 2024 的核心方法，逐步解释

2.1 为什么不用一个“大字典”保存整条 VLIW

假设一条宽指令有五个槽。完整五槽组合很多：即使每个槽单独只有 16 种常用值，整条指令也可能有 16⁵ 种组合。若把完整指令放进一张字典，字典很快就会太大。论文把指令按 issue slot 分成五个字段，每个字段用一张小字典。例如一条压缩指令不再保存五个原字段，而是保存五个字典索引。五张字典同拍读出，重新拼成一条完整 VLIW。

2.2 为什么不是所有指令都压缩

若一个很少执行的指令引入五个新字典项，它省下的一两次宽取指可能还不够支付字典装载和查表能耗。因此论文让编译器做选择：能反复复用已有字典项的指令压缩；其余指令继续以原宽形式存在。这样字典可以保持较小，也避免为了“压缩率好看”导致真实能耗变差。

2.3 为什么必须把多条压缩指令打成固定 Bundle

如果程序中任意混合 20-bit、30-bit、64-bit 指令，取指地址和跨界解码会很复杂。论文保持主指令存储的取指宽度不变：一个取指字要么是一条原宽指令，要么装固定数量的压缩指令。硬件读到压缩 bundle 后，将索引保存在小缓冲中，接下来逐周期查字典并输出一条完整指令。这样流水线填满后仍能每周期给后端一条指令。

2.4 为什么字典要在运行时重编程

不同程序、不同循环常用的指令字段并不相同。一套全程序静态字典要么很大，要么覆盖率很低。论文在编译时分析控制流图（CFG），把嵌套循环附近的基本块组成“压缩区域”；程序进入一个区域时先执行 header，再用若干个原宽字把新 frame 写入五张字典。论文避免在循环体内部反复改字典，而在进入循环区域时更新，以摊薄开销。

2.5 编译器如何挑字典项

不能简单地给每个槽独立选择最常见的值，因为一条指令只有在五个字段都能命中字典时才可压缩；而且还要连续凑够固定数量才形成 bundle。论文从内层循环开始，若整个循环所需项能放下就全部放入；放不下时，对候选 bundle 计算 occurrence-cost：大意是“新增多少字典项”除以“这些项在区域里能复用多少次”，优先选择花费小、复用多的联合组合。

2.6 它真正优化的目标

论文主要优化动态能耗，不是程序池容量。一个压缩 bundle 只需从较大的 L1/IMEM 读一次，却可以在几个执行周期中由小字典恢复多条指令。代价是：要读字典、保存 bundle 索引、装载 frame，并处理压缩/未压缩两种格式。论文因此用能量模型搜索字典深度，而不是只选择静态 bit 数最小的方案。

3. 用 FRV 的 174-bit 指令举一个完整例子

FRV 一条指令由五个 34-bit 功能槽组成，另有 3 个保留位和 1 个 EOP 位。这里使用两个保留位表示四种类型：未压缩、压缩 bundle、frame header、字典装载字。因此主存宽度仍保持 174 bit。

若直接使用原论文的五张字典容量数字 [32, 8, 8, 16, 32]，五个索引分别需要 [5,3,3,4,5] bit，一条压缩逻辑指令共 20 bit。一个 174-bit 取指字扣除 2-bit 类型后剩 172 bit，因此可以装：

floor(172 / (5+3+3+4+5)) = 8 条压缩逻辑指令

但这不等于“任何八拍都能压成一拍”。连续八条指令的五个槽值必须全部存在各自字典中；少一个字段不命中，整组就不能成为完整八条 bundle。进入该函数前还要读取一个 header，并用若干个 174-bit 字并行写入五张字典。硬件执行压缩 bundle 时仍连续输出八个原始周期，只是主 SRAM 在这八个周期里只读一次。

与 E2 的根本不同：E2 在每个原始周期内查看“哪些槽非 NOP”，保存至多四个 34-bit 有效值；Multanen 跨时间查看“连续多个周期的槽值是否能在字典中找到”。一个依赖空间稀疏，一个依赖值重复，二者的适用条件不同。

4. 原论文的平台与结果

项目论文设置应该怎样理解
处理器OpenASIP 生成的自定义 TTA；5 个 issue slot；最终指令 64 bit；静态调度，支持无条件分支和谓词执行。TTA 是显式控制数据搬运的静态多发射架构，可以看成比传统 VLIW 更暴露数据通路的一类机器。
控制位原始有效指令为 62 bit，增加 2-bit 字典控制，凑成 64 bit。这与 FRV 可使用保留位的思路相似。
五张字典最终容量为 32、8、8、16、32 项；每张对应一个 TTA issue-slot 字段。容量是对目标程序集做能耗搜索得到的，不是对所有 VLIW 都通用的常数。
Bundle每个 64-bit 取指字装三条压缩指令。bundle=3 是字典索引总宽度和 64-bit 取指宽度共同决定的。
字典硬件字典和 loop buffer 使用 latch-based register-file memory；28 nm、0.9 V、25℃、500 MHz，DC + 门级 SAIF/ModelSim。不能把本文的小 SRAM CACTI 数字当作原论文 latch-RF 面积。
程序CHStone 7 个、Embench 7 个；部分 Embench 因递归、64-bit 类型或浮点编译限制被排除。不是完整 22 个 Embench。
动态压缩率CHStone 0.71，Embench 0.69。运行时从上级存储读取的 bit 约减少 29%/31%。
静态压缩率CHStone 0.99，Embench 1.03。程序镜像几乎没变，Embench 甚至增大 3%；这再次证明它不是容量优先方法。
运行开销CHStone 平均 0.13%；Embench 各测例也接近可忽略。因为字典在进入热点循环前装一次，在循环多次迭代中摊薄。
系统能耗相对只有 L1 cache 的系统，再降 11.4%/3.8%；加入 loop buffer 后另有 19.8%/4.5% 平均收益。这些是整套特定存储层次结果，不能直接套到 FRV。

一个容易误引的面积数字：作者 2020 年单发射 RISC-V 前作报告过解压器约 4100 µm²、延迟 0.36 ns；2024 年论文没有给出五字典 TTA 解压器的可直接抄录绝对面积表。4100 µm² 不能当作 5-slot/174-bit FRV 解压器面积。

5. 能否取得原实验平台的 trace

5.1 已经能拿到什么

  • OpenASIP 官方仓库公开，可以生成 TTA/VLIW 类处理器、编译程序和产生 ISA trace。
  • CHStone 源程序公开；当前 OpenASIP 仓库也包含多项 CHStone 测试源码。Embench 本身也是公开 benchmark。
  • 论文全文公开，架构总宽、issue 数、最终字典容量、bundle 大小、工艺与评估流程都能确认。

5.2 仍然缺什么

缺失 artifact为什么不可替代当前查证结果
论文使用的 TTA .adf/.bem决定五个 issue-slot 的精确位宽、功能单元、互连、立即数字段和最终 62-bit 编码。论文没有附件链接，当前官方仓库未发现与该论文对应的固定机器文件。
编译后的 TPEF/程序镜像同一个 C benchmark 在不同机器定义、编译器版本和调度参数下会产生不同 VLIW。未发现作者实验用二进制。
动态 ISA trace 与输入动态 CR 和能耗依赖分支路径、循环次数与 cache miss。论文只给统计图，没有逐周期 trace 数据。
2024 CFG/区域/字典选择代码它决定哪些循环组成区域、哪些指令压缩、何处装载 frame。当前官方 OpenASIP 仓库只有较早的通用静态插件 InstructionDictionary.cc 和 MoveSlotDictionary.cc；文件说明分别是整指令静态字典和 move-slot 静态纵向字典，作者/年代为 2005–2009，并不是 2024 的可编程选择性算法。
五字典解压器 RTL/SAIF决定真正的面积、时序、查表和 bundle-buffer 能耗。论文说明做过 RTL/门级验证，但未发现对应公开 artifact。

表头说明：第一列是复现实验必需文件；第二列解释为什么只有公开 benchmark 源码仍不够；第三列是截至 2026-09-10 对论文、作者页面和 OpenASIP 官方仓库的查证。

结论：目前不能拿到“原论文可直接使用的逐周期 trace”，所以不能声称已经复现其 0.71/0.69。可以从公开 OpenASIP 和 benchmark 重新建立一个相似平台，但结果会是独立复现，不一定等于论文平台。最有效的做法是联系作者，索取：TTA ADF/BEM、编译后二进制、动态 trace、compression-region/frame 文件、压缩器源码和解压 RTL。

5.3 即使拿到 trace，也未必能直接跑 E2

E2 当前要求逻辑槽等宽。论文给出五个字典字段和总计 62+2 bit，但没有在正文表中列出五个字段的精确等宽关系；TTA 的 move-slot 编码通常随可连接源/目的数量而变化。拿到 ADF/BEM 后必须先确认：

  1. 五个字段是否等宽；若不等宽，不能直接称为“4×34-bit E2”。
  2. 最终 executable 每拍非 NOP 槽峰值是否≤4，而不是只看平均利用率。
  3. 若用补齐到最大字段宽度的方法强行等宽，必须把 padding 增量同时计入 raw、纵向和 E2，不能只让 baseline 承担。

因此，现阶段最公平且可立即执行的对比是：把 Multanen 的方法移植到 FRV 的同一批 trace，而不是凭论文图推测 TTA trace 后声称 E2 胜出。本报告已经完成前者。

6. E2 与 Multanen 应比较什么

维度Multanen 可编程并行字典E2 四 Lane 条带化
利用的冗余多个周期之间出现相同的 slot 字段值。一个周期内五个槽经常只有 1–3 个有效。
可接纳条件完整连续 bundle 的每个字段都必须命中字典；不命中可回退原宽。最终 trace 每拍有效槽数≤4；超过就必须重调度或加侧道。
主存读取压缩 bundle 的多个执行周期只取一个原宽字。Config 每周期读取；只对本拍实际事件读取 payload Lane。
主存容量取决于插入 header/字典项后的静态字数是否跨 2 次幂深度档。由 Config 深度和四条有效事件流深度决定。
运行开销换 frame 时需要停顿写字典；热点循环可摊薄。合法 max-4 trace 不增加执行周期；固定流水启动延迟。
主要硬件五张可写小字典、五路索引、bundle 缓冲、类型/区域控制。Config SRAM、四个事件计数器、phase、4→5 散布网络。
适合的程序循环中完整字段值高度重复，且 frame 能重复使用很多次。槽值可以很杂，但同拍并发峰值低、NOP 多。

7. 将 Multanen 方法应用到 FRV-SFU-VLIW

7.1 实验设置和证据边界

  • 输入为现有 BERT、LLaMA、SD-UNet 三个程序池的全部 issue-5 schedule.txt，共 12 个函数成员、11 种不同函数/尺寸。
  • 五个 34-bit slot 分别使用一张字典；两个保留位用作类型标记；EOP 保持未压缩。
  • 每个非线性函数视为一个 compression region。候选连续 bundle 按“新增字典项/静态复用次数”排序并联合选项；若 header+字典项+压缩正文不能减少该函数主 SRAM 读取，则整个函数回退未压缩。
  • 编码后逐条恢复原始五个 slot、reserved 和 EOP；所有选择的配置均 bit-exact 通过。
  • 这叫基于论文机制的 trace 估计，不是其未公开 CFG 编译器复现。FRV 的展开式静态调度也没有原论文热点循环的动态 profile。

表头说明：“主存读取比”是插入 frame 后实际读取的 174-bit 主存字数/原周期数；E1/E2 使用不同的多 Bank 组织，不适合用这个单一比例，故写“—”。“请求存储 bit”按逻辑宽度和 2 次幂深度计算；Multanen 行还加一套共享硬件字典的逻辑 bit。“面积”仅含 CACTI SRAM；Multanen 的小字典用 SRAM 作代理，而原论文实际用 latch-RF。“动态能量”对 E0/E1/E2 是执行期读能量；Multanen 还计入字典查表和 frame 写入，但所有行都未计组合逻辑/时钟树。因此只作方向筛选。

7.4 怎样读这张表

  1. Multanen 确实有效，但目标不同。128×5 筛选点相对 E0 将一次池运行的存储动态能量降低约 18.5%、16.2%、23.5%。所以不能说“字典完全无效”。
  2. 它没有让 FRV 主程序 SRAM 变浅。BERT 压缩后 6068 字，仍需 8192 深；LLaMA 25460 字仍需 32768 深；SD-UNet 8702 字仍需 16384 深。主 SRAM 面积与 E0 相同，再加字典后略大。
  3. E2 的 SRAM 组织优势更强。E2 面积约是字典筛选点的 21.8%、37.5%、19.4%；动态存储能量约是字典点的 19.2%、30.7%、26.8%。即使暂时不计 Multanen 更复杂的 bundle buffer 和控制逻辑，E2 仍明显更低。
  4. 大字典改善读取，却增加启动开销。128×5 需要在每个函数入口装更多项，额外周期达到 BERT 6.73%、SD-UNet 5.52%。原论文能把开销压到 0.13%，依赖热点循环大量重复执行；FRV 展开式微程序不具备同样摊薄条件。

7.5 能否在 E2 后面再加字典

初步数据不支持把它作为近期主线。E2 已删除全部 NOP，四条 Lane 中剩下的几乎都是带不同寄存器/地址的有效 34-bit 字：

  • BERT 每 Lane 约 1,587–1,680 个不同值，出现一次的值约 1,433–1,592 个；最常见 64 项只覆盖 7.9%–9.9% 事件。
  • LLaMA 每 Lane 约 5,860–6,274 个不同值，最常见 64 项只覆盖 6.5%–7.1%。
  • SD-UNet 每 Lane 约 2,723–2,913 个不同值，最常见 64 项覆盖 10.4%–14.1%。

E2 的优势之一正是把 NOP 去掉；但 NOP 又是字典最容易命中的值。把字典放到 E2 payload 后面，反而失去字典最主要的重复来源，还要增加四张字典和索引/逃逸编码。因此目前不建议做“E2+payload 字典”RTL，除非先引入字段级 bitmask/delta，使寄存器地址变化不再破坏匹配。

8. 将 Multanen 方法应用到 OpenEdgeCGRA 的 12 个公开映射

8.1 实验怎样做

  • 使用固定官方仓库 commit 对应的 12 个可执行 mapping 生成器，共 348 个 context 行；每行四个 32-bit RC row word。
  • 每个公开 mapping 作为一个可编程字典区域；四张 16-entry×32-bit 字典；每条压缩逻辑行需 16-bit 索引，因此一个 128-bit context 字扣除 2-bit 标签后可装 7 行。
  • 若某个 mapping 插入 header/字典项后不能减少读取字数，就保持未压缩；最终 8/12 个 mapping 使用字典。
  • 所有压缩行逐 row、逐 slot 精确恢复。12 映射池是超过默认 context depth=128 的压力池，因此下表是扩容设计研究，不是原版 OpenEdge 可直接部署容量。

8.3 为什么 OpenEdge 上不建议把 Multanen 作为主方案

  1. 它通过 247 个存储字将主 context 深度从 512 降到 256，但还要四张字典；总逻辑 bit 恰好与 phase-seeded E2 同为 34,816，CACTI 面积反而高约 4.8%。
  2. 字典总动态能量比 phase-seeded E2 高约 19.9%，还未计 bundle buffer、查表 mux 和字典控制。
  3. 12 个 mapping 很短，frame 装载无法像原论文热点循环那样摊薄；保守计算增加 103 个装载周期，即 +29.6%。
  4. 该压力池完整四槽 bundle 的重复性很强，简单静态整 bundle 字典反而更小。若强调未知程序可替换，静态字典的内容必须随程序池一起重新装载；这需要另行定义部署协议，但仍说明“并行可编程字典必然最好”不成立。
OpenEdge 的公平论文角色：把 Multanen 列为正式软件 baseline，并报告它确实跨过深度档；随后用面积、能耗和装载开销说明 E2 更适合“context 稀疏、需快速顺序恢复”的场景。不要只比较未取整字数，也不要把 kernel 装载开销误写成计算周期。

9. CCF 4×4 CGRA：重新从零解释

9.1 “4×4”不是“四个指令槽”

CCF 的 4×4 表示有 4 行×4 列，共 16 个 PE。如果把每个 PE 在某周期的 64-bit 控制字看成一个逻辑槽，那么这里是 M=16，不是 M=4。你的 E2 若设置 N=4，含义是：原来一拍最多可能有 16 个 PE 指令，但物理只提供四条 payload Lane；要保持原周期，一拍有效 PE 数必须≤4。

9.2 为什么旧结论说“不影响周期”，后来又被推翻

CCF 仓库同时存在两个层次的文件：

文件层次里面有什么simple_loop_1 看到的结果能否代表最终执行
.sch mapper 调度片段映射器安排的 kernel node/PE 占用，不包含完整机器控制的所有阶段。11 周期、21 个有效事件、峰值 3 个 PE 同拍。不能。它遗漏配置、预装载和收尾。
prolog/kernel/epilog_ins.bin 最终机器流模拟器/执行端真正消耗的 16×64-bit 周期字，包括 prolog、kernel、epilog。39 周期、67 个有效 PE 字；存在一拍 16 个 PE 全部有效。这是判断 E2 接纳性的正确输入。

表头说明：“.sch”回答 mapper 如何放 kernel；“最终机器流”回答硬件每拍必须恢复什么。只有后一行可以决定 N=4 是否保持周期。

9.3 16 槽同拍对四 Lane 意味着什么

原始一拍：16 个有效 PE 控制字
纯 E2 每拍容量：4 个有效控制字
只按数量拆分的乐观下界：ceil(16/4)=4 拍，即这一拍至少多 3 拍

因此 simple_loop_1 即使忽略依赖和路由冲突，也至少从 39 拍变成 42 拍，增加 7.7%。这已经违反“每周期恢复原完整指令”。仓库另外三组 15-cycle mapper schedule 的峰值为 10–12 个有效 PE，同样不适合 N=4；仅按数量拆拍的乐观额外周期分别达到 +86.7%、+100% 和 +113.3%。

9.4 为什么“相同值多播”又能在 simple_loop_1 上工作

那一拍虽然有 16 个有效 PE，但 16 个 64-bit 字只有两种不同值。如果一条物理 Lane 读一个值，同时再带 16-bit 目的位图，就可以把同一个值发给多个 PE；四条 Lane 足够容纳最多四种不同值。软件验证显示这条 39-cycle binary 每拍最多三种不同有效值，因此“4 value-lane + 多播”可以无损恢复。

但它不是 E2。E2 每拍只需一个 16-bit 有效槽 mask，每个 Lane 对应一个事件；多播方案需要四个 16-bit destination bitmap，共 64-bit metadata，并需要一对多分发网络。更重要的是，其它 CCF schedule 没有对应完整机器字，无法验证它们是否也只有≤4种值。因此只能说 simple_loop_1 支持多播扩展，不能说“CCF 支持纯四 Lane E2”。

9.6 CCF 是否已有指令压缩

CCF 官方仓库和原论文主要提供 CGRA 编译、映射、模拟和代码生成；最终 *_ins.bin 仍显式保存 NOP，没有发现论文自己的指令压缩机制。OpenASIP 仓库中的通用静态字典插件也不是针对 CCF 的实现。当前最严谨结论仍是：截至 2026-09-10，未找到已公开的 CCF 专用指令压缩工作。

CCF 在第四篇论文中应是什么角色：它不是 E2 的正向跨平台证据，而是一个很有价值的失败反例：只看平均稀疏度或简化 mapper schedule 会错误判断 N=4 接纳性；必须分析最终 executable 的逐周期峰值。如果未来取得更多完整 CCF binary，它更适合研究“按不同值数量接纳的多播扩展”，而不是硬套纯 E2。

10. 第四篇论文应怎样纳入 Multanen baseline

10.1 建议的对比层次

  1. 算法层：同一 FRV trace 比较 E0、Candidate A、E2、Multanen-shaped programmable dictionary；报告逐 bit 恢复。
  2. 静态存储层：报告未取整字数、2 次幂取整后的 SRAM 总 bit、物理宏宽/深，解释是否跨档。
  3. 动态层：报告主存读取数、payload/dictionary 读取数、frame 写入数和一次调用能量；不能把 static CR 当 dynamic CR。
  4. 性能层：E2 报告 max-4 调度是否增周期；字典报告 frame 装载周期，并区分循环迭代摊薄和单次微程序调用。
  5. 硬件层：最终需要一个真正的五字典 FRV RTL baseline，至少包含索引缓冲、五张可写字典、旁路、header/entry 控制和逐周期恢复；在完成前，本文数字只能标“software + CACTI proxy”。

10.2 可以成立的论文论点

推荐论点：现有可编程字典通过跨时间的值重复降低动态取指能耗，但在宽 VLIW 的字段值被寄存器/地址编码扰动、静态程序池需按离散 SRAM 宏定容时，不保证降低本地程序存储容量。本文针对另一类普遍冗余——逐周期 issue-slot 稀疏——提出逻辑槽/物理 Lane 解耦的条带化存储，在满足逐周期峰值接纳条件时，不依赖值重复即可精确恢复；并用 Multanen 字典、传统纵向方法和失败平台反例界定适用范围。

10.3 暂时不能写进论文的过度结论

  • 不能写“完整复现 Multanen 2024”，因为原 CFG 后处理器、TTA 文件、trace 和五字典 RTL 尚未公开取得。
  • 不能把 4100 µm² 当作其 TTA/FRV 解压器面积；那是 2020 RISC-V 前作。
  • 不能只用本报告的 128×5 搜索点代表作者算法全局最优；它只是 39 个固定配置、本文启发式和 CACTI 小 SRAM 代理下的最佳点。
  • 不能说字典在 FRV “没有收益”；它相对 E0 减少了动态宽存储读取。准确结论是：它没有降低三池的主 SRAM 深度，且不如 E2 的存储组织。
  • 不能继续把 CCF 写成纯 E2 零损失平台。

10.4 下一步最小工作

  1. 给 Multanen 作者发送 artifact 请求；若拿到原 TTA trace，先检查 slot 位宽与最终逐拍占用，再判断是否能直接跑 E2。
  2. 把本次 Python estimator 固定为论文软件 baseline，增加单元测试：空区域、单条 EOP、bundle 边界、回退未压缩、frame 切换和非连续程序切换。
  3. 实现一个最小 FRV 五字典 RTL，只做本报告的固定“每函数一 frame”版本；综合得到 1 GHz 下真实面积、功耗和 bundle-buffer 关键路径。它不需要先复刻完整 CFG 编译器。
  4. 若五字典 RTL 明显大于 E2，正文仍公平报告；若动态能量在某些高复用函数胜出，则可提出“编译时按 trace 特征选择 E2 或字典模式”的双模式扩展，但必须先证明额外模式位与两套解码路径不会抵消收益。
